# Database adapter boundary

Decision for `mbs-8g5.12.6`, 2026-09-24. This concerns Message Box Store as an independent package.

Store supports its in-memory repository, persistent SQLite through `node:sqlite`, and MySQL through Knex with the `mysql2` driver. `HistoryRepository` in `src/storage.ts` is the public behavior boundary; the raw `./repository`, `./repository.sqlite`, and `./repository.mysql` package paths expose the corresponding runtime implementations. The standalone service accepts a host-supplied `ServiceKnex` or `HistoryRepository`, but its default migration, config, and readiness path remain MySQL-specific. Injection permits custom composition; it does not certify another SQL dialect.

The sister Message Box Server's `createMessageBoxContext` likewise accepts a host-supplied Knex instance. Its `knexfile.ts` lets the operator set `KNEX_DB_CLIENT` and defaults to `mysql2`. Its repository code mainly uses Knex's query builder, and the reference tests create a MySQL-configured Knex handle. This is a looser connection boundary, not proof that every client supported by Knex passes its migrations and behavior tests.

Store needs more than query syntax portability. SQLite uses `BEGIN IMMEDIATE` and `node:sqlite` prepared statements. MySQL uses InnoDB `FOR UPDATE` owner/resource locks, deadlock and lock-wait retries, `ON DUPLICATE KEY`, SQL `LIMIT` mutation behavior, and explicit timestamp conversion. Migrations ship distinct MySQL and SQLite DDL and checksums, then verify dialect-specific catalog structure (`INFORMATION_SCHEMA`/`SHOW CREATE TABLE` versus `sqlite_master`/PRAGMA). Cursor ordering, fixed-watermark reads, rollback, deletion fences, and unsigned 64-bit sequence handling are adapter invariants. A generic Knex connection would not supply those guarantees automatically.

Keep the existing repository interface as the openness mechanism. Share pure policy where it demonstrably reduces source and passes parity tests, as with feed preparation; retain dialect-specific transaction, migration, locking, and timestamp code. No new SQL dialect is claimed or implemented in this refactor. A future adapter should be a bounded independent task: implement `HistoryRepository`, migrations and structural verification for the named dialect, then pass the existing conformance and concurrent mutation tests against a dedicated database. A shared SQL layer is justified only after a third adapter reveals substantial duplicate query semantics that can be centralized without hiding transaction guarantees.
